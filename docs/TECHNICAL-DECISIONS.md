## 📦 Архітектура

### Чому Turborepo monorepo?

`web`, `api`, `worker` — три окремі Docker-образи з різними базовими образами (Alpine vs Ubuntu). Monorepo дозволяє:
- Спільні TypeScript типи через `packages/shared-types` без публікації в npm
- Єдиний `pnpm-lock.yaml` — детермінована збірка
- Turbo кешує build/lint/test — швидше в CI

### Чому три окремі застосунки (web / api / worker)?

- **web** (Next.js): SSR, SEO, клієнтська частина — потребує Node 20 Alpine
- **api** (Fastify): REST API, бізнес-логіка — легкий Alpine образ, ~200MB
- **worker** (BullMQ): обробка файлів через LibreOffice/Pandoc/Ghostscript/Calibre — потребує Ubuntu 22.04, ~1.5GB. Не можна поєднати з api бо системні залежності забруднять образ.

### Чому Fastify, а не Express або Hono?

- Fastify швидший за Express (benchmark: 2–3x)
- Вбудована схема валідації через JSON Schema
- Plugin система з version checking (уникає несумісних плагінів)
- TypeScript support з коробки
- Hono розглядався але Fastify має кращу екосистему для Prisma/BullMQ

### Чому PostgreSQL, а не MongoDB?

Дані платформи — реляційні: User → Book → Order → OrderItem → Royalty. PostgreSQL дає:
- Foreign keys та транзакції для фінансових операцій
- `tsvector` для fulltext пошуку (без ElasticSearch)
- JSONB якщо потрібна гнучкість
- Prisma ORM підтримує PostgreSQL краще за MongoDB

### Чому MinIO, а не S3?

- Self-hosted на тому ж VPS — zero egress cost
- S3-сумісний API — при масштабуванні легко перейти на AWS S3 або Cloudflare R2
- Файли авторів (DOCX, EPUB, PDF) — великі, постійний доступ через signed URLs

## 🔐 Авторизація

### NextAuth.js v5 + JWT strategy

- **Чому NextAuth**: готова інтеграція з Next.js, підтримує Google OAuth без зайвого коду
- **JWT (не database sessions)**: авторизація без зайвих запитів до БД на кожен request
- **Env змінні NextAuth v5**: `AUTH_SECRET` (не `NEXTAUTH_SECRET`), `AUTH_URL` (не `NEXTAUTH_URL`)
- **Google OAuth**: додатковий канал реєстрації, популярний серед авторів
- **Caddy routing**: `/api/auth/*` → `knyha-web:3000` (Next.js обробляє), `/api/*` → `knyha-api:3001` (Fastify)

### API JWT (Fastify)

Fastify використовує окремий JWT для авторизації API запитів (middleware). Секрет зберігається в `NEXTAUTH_SECRET` env змінній API. Це НЕ той самий секрет що NextAuth використовує для своїх сесій — вони можуть збігатись або різнитись.

## 📚 Обробка книг

### Формати та конвертація

| Формат | Інструмент | Призначення |
|---|---|---|
| PDF (screen) | LibreOffice headless | Онлайн перегляд, продаж |
| PDF/X-3 (print) | Ghostscript | Друкарня — CMYK, 300 DPI, bleed 3мм |
| EPUB 3 | Pandoc | Електронні читалки, D2D, Google |
| FB2 | Calibre | Популярний у СНД формат |
| MOBI/AZW3 | Calibre | Amazon Kindle |

### Чому Ubuntu 22.04 для worker (не Alpine)?

LibreOffice, Pandoc, Ghostscript і Calibre мають складні системні залежності (glibc, fonts, python). На Alpine вони або не збираються або потребують musl compatibility шарів. Ubuntu 22.04 — стабільна база, пакети в apt. Розмір образу ~1.5GB — прийнятно для worker.

### Черга BullMQ + Redis

- Конвертація може тривати 30–120 секунд — не можна блокувати HTTP request
- BullMQ дає retry логіку, delay, priority, dead letter queue
- Redis вже використовується для кешу — одна інфраструктура
- Кожен формат — окремий job (паралельна конвертація)

### Валідація print PDF

Якщо PDF/X-3 (print) < 10MB — повторити без стиснення. Маленький розмір = втрата якості неприйнятна для друкарні.

## ✍️ Редактор рукопису (текст + зображення)

### Чому TipTap?

`ManuscriptEditor` (`apps/web/components/manuscript/ManuscriptEditor.tsx`) на сторінці `/dashboard/books/[id]/manuscript` побудований на **TipTap v3** (`@tiptap/react`, `@tiptap/starter-kit`, `@tiptap/extension-text-align`, `@tiptap/extension-underline`) — найпоширеніший production rich-text редактор у React/Next.js екосистемі (обгортка над ProseMirror, MIT, активно підтримується). Контент зберігається як **ProseMirror JSON** (не HTML, не Markdown) у полі `Book.manuscriptContent` (`Json?` в Prisma), автозберігається через `PATCH /api/books/:id/manuscript` (`apps/api/src/modules/books/manuscript.ts`, приймає `content: z.any()` — бекенд не валідує структуру документа, тож нові типи нод не потребують міграції схеми).

Кастомні атрибути додаються офіційним механізмом TipTap `Node.extend({ addAttributes() {...} })` — так само зроблено `StyledParagraph` (`apps/web/components/manuscript/styledParagraph.ts`, атрибут `style` для розділів/глав/цитат/віршів) і `ResizableImage` (нижче).

### Зображення в тексті

`apps/web/components/manuscript/resizableImage.ts` розширює **офіційний** `@tiptap/extension-image` (не сторонній/самописний пакет):
- **Resize** — вбудована функція пакета (`resize: { enabled: true, directions, minWidth, minHeight, alwaysPreserveAspectRatio }`), рендерить ручки зміни розміру через `data-resize-handle` — стилізовано в `<style jsx global>` блоці `ManuscriptEditor.tsx`, логіка перетягування вся всередині пакета
- **Позиціонування** (ліворуч/по центру/праворуч, з обтіканням текстом для лівого/правого) — власний атрибут `align`, рендериться як `data-align` на `<img>`; обтікання реалізоване чистим CSS (`float` + селектор `:has()` на `[data-resize-container]`), без кастомного node view
- Кнопка "Вставити зображення" в тулбарі + drag&drop і paste прямо в текст (`editorProps.handleDrop`/`handlePaste`, офіційний API TipTap)
- Завантаження файлу: `POST /api/books/:id/manuscript/images` (`apps/api/src/modules/books/manuscript-image.ts`, за зразком `cover.ts`) → MinIO `public/manuscripts/{bookId}/{uuid}.{ext}` → повертає `{ url }`, який вставляється в документ через `editor.commands.setImage({ src: url })`. URL зображення живе тільки всередині `manuscriptContent` JSON — окремого поля в `Book` не потрібно.

## 👁️ Передперегляд книги

### Чому react-pageflip-enhanced?

`BookViewer.tsx` (`apps/web/components/books/BookViewer.tsx`, `/dashboard/books/:id/preview`) використовує `react-pageflip-enhanced`, а не оригінальний `react-pageflip` — оригінал не оновлювався ~5 років, форк додає touch/swipe і лишається сумісним за API. Джерело сторінок — не PDF "на льоту" і не `manuscriptContent`, а заздалегідь зрендерені PNG (`generate-page-thumbnails.ts` в `apps/worker`, Ghostscript з готового `book.pdfUrl`, окремо кольоровий і ч/б через `sharp().grayscale()`), кожна сторінка — просто `<img>` всередині листа флipbook.

### `showCover` — обкладинка як твердий лист флipbook, а не окрема вкладка

До 2026-08-10 вкладка "Обкладинка" була повністю ізольованим статичним переглядом (`<img>` + range-повзунок перед/зад, миттєва зміна `src`), а сам флipbook (`showCover={false}`) відкривався з ручного порожнього "blank leading page", щоб сторінка 1 відкривалась праворуч (recto) — перехід між "Обкладинка" і "Кольорова книга" був стрибком між двома різними UI-блоками.

Бібліотека сама підтримує реалістичне розгортання палітурки через `showCover: true` (`node_modules/react-pageflip-enhanced/build/page-flip/Settings.d.ts`: "the first and the last pages will be marked as hard and will be shown in single page mode"). Тепер, коли в книги є `coverUrl`, обкладинка — перший твердий лист того самого флipbook (`showCover={!!coverUrl}`), а перехід із закритої книги у внутрішній розворот — плавна анімація перегортання, не перемикання компонентів. Оскільки `showCover` фіксує пару лише для листа 0 (і останнього), одразу після обкладинки вставлено порожній лист-розпірку — це зберігає ту саму recto-конвенцію (сторінка 1 праворуч), що раніше давала ручна вставка `null` на позицію 0. Вкладка "Обкладинка" як окремий статичний перегляд (в т.ч. `backCoverUrl` — художнє оформлення задньої сторони) лишилась — вона про огляд самого дизайну обкладинки, а не про читання книги.

## 🖼️ Редактор обкладинки

### Fabric.js залишається, Polotno SDK — ні (рішення 2026-08-10)

Перед переробкою `CoverDesignerCanvas.tsx` під реальний перемикач форматів (T-1914) оцінили [Polotno SDK](https://polotno.com) — має власну документацію саме про "book cover editor" (locked-шаблони, авто-вписування зображень у форму, палітри/патерни — точно те, що потрібно). Але це платний self-hosted SDK: **$249/міс** (обмежений об'єм рендеру) або **$899/міс**. Перевірили GitHub на безкоштовні альтернативи — нічого продакшн-готового немає, є лише сирі "canva-clone" туторіальні репозиторії (Layerhub, react-design-editor), самі побудовані поверх Fabric.js/Konva, тобто не дають нічого понад те, що вже є в проєкті. Ulit — bootstrapped проєкт із self-hosted інфраструктурою всюди (MinIO замість S3, власний ISBN-сервіс замість платного API) — платити щомісяця за SDK заради фіч, які можна домалювати над уже робочим Fabric.js-редактором, нелогічно. Рішення: лишаємось на Fabric.js, бракуючі можливості (locked-слот, палітри, патерни) реалізували самі поверх нього.

### Параметричний `CoverLayout` замість жорстких DISPLAY_W/H

До 2026-08-10 всі 6 шаблонів малювали напряму в константи `DISPLAY_W=350, DISPLAY_H=525` — робити реальний перемикач форматів (не фейкову кнопку) означало б рефакторити всі шаблони, тому T-1914 було свідомо заблоковано ще 2026-08-08. Тепер кожен `Template.apply(canvas, ctx)` отримує обчислений `computeCoverLayout(format, pageCount)`: для `ebook` — один canvas (тільки перед), для `softcover`/`hardcover` — розгортка `back + spine + front` в один canvas, ширина корінця — `pageCount × 0.1мм` (+4мм для твердої, спрощена різниця "лише трохи інші пропорції", а не окрема система шаблонів) переведена в px тим самим масштабом, що й export-роздільність (1800px / 300dpi ⇒ px/мм).

### Locked photo-слот — `clipPath` + cover-fit, не вільний фон

"Завантажити ілюстрацію"/"Випадковий паттерн" вставляють зображення чи паттерн (`fabric.Group` із самостійно намальованих фігур — крапки/смуги/сітка/кола, без сторонніх asset-паків) у передню панель через `fabric.Image` з `clipPath: { absolutePositioned: true }`. Ключовий момент: clipPath прив'язаний до координат canvas, а не до трансформації самого об'єкта — тому зображення можна двигати/масштабувати (`lockUniScaling: true` — тільки пропорційно) прямо всередині цієї рамки, і це природно дає ефект панорамування/кропу без окремого "режиму обрізки".

### `fabric.Textbox`, не `fabric.IText`

Перший прохід використовував `IText` для назви/автора/анотації — виявилось, що `IText` **не переносить текст автоматично** за шириною (`width` — лише інформаційне поле, перенос тільки вручну через Enter). `Textbox` (той самий базовий API, розширює `IText`) рахує перенос рядків і фактичну висоту синхронно в конструкторі — це дало можливість підправити висоту напівпрозорої плашки під заголовком під реальну (переносну) висоту тексту, а не фіксовану частку висоти панелі (інакше довгий заголовок на 3-4 рядки наїжджав на підзаголовок).

### Стандартизований колофон і "підлога" шарів

Задня сторінка друкованих форматів: ISBN-текст завжди безпосередньо над штрихкодом (`jsbarcode`, EAN-13), лого сервісу (`/figma/logo-group.svg`) + підпис "Платформа самовидавництва для українських авторів" — праворуч від штрихкоду, позиція рахується від реально виміряної ширини штрихкоду (не хардкод), щоб не накладалось при різній довжині ISBN.

Керування шарами (`front/back/forward/backward`, з'явилось із живого тестування) має "підлогу" — `backgroundFloorIndex()` не дає тексту чи прямокутникам-плашкам опуститись позаду фону (кольору чи зображення): фонові об'єкти (`role: "accent"`, `role: "bg-image"`) завжди йдуть суцільним блоком з індексу 0, і "На задній план"/"Перемістити нижче" зупиняються рівно над ними.

## 🌍 Дистрибуція — ручна vs автоматична

### Поточна модель (MVP): повністю ручна

Адмін отримує чергу книг → завантажує ZIP пакет (EPUB + обкладинка + metadata.csv) → вручну завантажує на кожен сервіс.

| Сервіс | Статус | Причина |
|---|---|---|
| **Amazon KDP** | Ручна | KDP Selling Partner API вимагає офіційної заявки та схвалення Amazon. Процес: подати заявку → чекати схвалення (тижні/місяці) → отримати API credentials |
| **Draft2Digital (D2D)** | Ручна | D2D Partner API вимагає Business Development угоду. Контакт: bizdev@draft2digital.com |
| **Google Play Books** | Ручна | Google Books Partner Center API — закрита програма, потребує заявки |
| **Власний магазин** | Автоматична | Одразу після публікації |

### Стратегія дистрибуції автора

**WIDE (Широке)**: книга потрапляє в чергу адміна → D2D + KDP + Google (вручну)  
**KDP_SELECT (Ексклюзив Amazon)**: тільки Amazon 90 днів. Система автоматично знімає з інших платформ. За 7 днів до закінчення — email автору.

### Майбутня автоматизація (Фаза 2)

- Після схвалення KDP SP API → автоматично завантажувати через API
- D2D планує відкрити API — слідкувати за їх блогом
- Google Books — при партнерстві Google надає доступ до Content API

## 💳 Платежі

### Вибір провайдерів

| Провайдер | Статус | Для кого |
|---|---|---|
| **LiqPay** | Реалізовано (MVP) | Українські картки (Приват24, Монобанк, Visa/MC) |
| **WayForPay** | Планується (Фаза 2) | Альтернатива LiqPay, популярна в Україні |
| **Stripe** | Планується (Фаза 2) | Міжнародні картки, Google Pay, Apple Pay |

### Чому LiqPay першим?

- Найпоширеніший в Україні — інтеграція з Приват24 і Монобанком
- Проста інтеграція через form + signature
- LiqPay Payback API — майбутні виплати авторам на картки Приват24

### Архітектура callback

Після оплати → LiqPay → `POST /api/payments/liqpay/callback` → verify signature → оновити Order.status = PAID → надіслати email з signed URLs (48 год).

## 💸 Система виплат авторам

### Бізнес-модель

- **Комісія платформи**: 25% від кожного продажу (змінюється через `PLATFORM_FEE_PERCENT` env)
- **Автор отримує**: 75% від ціни книги мінус комісія платіжного провайдера (~2.5%)
- **Мінімальний поріг виплати**: 500 UAH

### Hold period (витримка 7 днів)

Гроші блокуються на 7 днів після продажу перед виплатою. Причина: захист від chargebacks (покупець може скасувати оплату протягом 7-14 днів). Практика всіх marketplace (Etsy, Gumroad, Amazon).

### Виплата Phase 1 (ручна)

Автор запитує виплату → адмін бачить чергу → відправляє вручну через LiqPay або банківський переказ → позначає як виплачено.

### Виплата Phase 2 (автоматична)

- LiqPay Mass Payments B2P API → автоматичний переказ на картку Privat24
- WayForPay Settlement API → будь-яка українська картка
- IBAN (SWIFT/SEPA) → для ФОП з розрахунковим рахунком

### Податкова відповідність (Україна)

- При реєстрації автор вказує тип: **фізична особа** або **ФОП (Фізична особа-підприємець)**
- Зберігається **РНОКПП** (реєстраційний номер облікової картки платника податків)
- ФОП самостійно сплачує податки (єдиний податок)
- Фізособа — платформа має інформувати про необхідність декларування доходів
- CSV звіт для бухгалтерії: ПІБ, РНОКПП, сума, дата виплати

## 🔄 Флоу модерації та публікації книги (задокументовано 2026-08-09)

> Уточнено Анатолієм в чаті — реальний ручний процес, а не декоративний UI. Може змінитись пізніше, тоді оновити цей розділ.

Це модерований флоу — книга ніколи не стає `PUBLISHED` одразу після дії автора. Задіяні два незалежні статуси: `Book.status` (DRAFT → PROCESSING → REVIEW → PUBLISHED) і `Book.publicationTimeline` (JSON, довільні кроки з датами — див. нижче), плюс окремо `d2dStatus`/`kdpStatus`/`googleStatus` для зовнішніх майданчиків.

### Кроки

1. **Автор завантажує рукопис** → worker конвертує → `conversion-status.ts` ставить `status = DRAFT` щойно конвертація завершилась (успіх чи ні) — конвертація сама по собі НЕ ставить книгу в чергу на модерацію, `REVIEW` можливий лише через свідому дію автора (крок 2).
2. **Автор тисне «Надіслати на модерацію»** (дашборд книги, `POST /api/books/:id/publish`) — валідує обов'язкові поля (обкладинка/рукопис/ціна) і **вимагає, щоб `User.contractAcceptedAt` вже було встановлено** (інакше 400 `CONTRACT_NOT_SIGNED`, автора направляють на `/dashboard/settings/contract`), ставить `status = REVIEW` (якщо ще не) і `publicationTimeline.submitted = now`. **Це НЕ публікація** — книга ще ніде не видима. *(До T-1951 контракт акцептувався тут же мовчки, автоштампом — тепер це окрема, явна, one-time дія автора в профілі, див. розділ «Юридика» нижче.)*
3. **Адмін бачить книгу в черзі** (`status = REVIEW`, admin dashboard/`/admin/books`) і тисне «Схвалити» (`PATCH /api/admin/books/:id/approve`) — ставить `publicationTimeline.review_done = now`. Це теж **НЕ публікація**, лише позначка "перевірку пройдено".
4. **(За потреби) Адмін просить повторну перевірку документів автора для цієї книги** — вручну через форму `PATCH /api/admin/books/:id/publication-timeline` (кроки `contract_pending`/`contract_corrected`/`review_2`). Це вже не «підписання договору» (він підписаний заздалегідь, разово) — на фронтенді ці кроки показані як підпункти одного рядка «Укладання договору».
5. **Адмін публікує книгу** — ставить дату на кроці `contract_signed` через ту саму форму (назва ключа лишилась історичною, автору показується як «Публікація у магазинах»). **Це і є момент фактичної публікації**: бекенд автоматично призначає ISBN, ставить `status = PUBLISHED`, `publishedAt = now`, активує KDP Select (якщо обрано), шле email автору. Книга стає видимою в магазині Ulit — це "перше" місце публікації.
6. **Адмін відправляє файли на зовнішні майданчики** (Amazon KDP, Draft2Digital, Google Play Books) — окремо, вручну, через `PATCH /api/admin/books/:id/distribution` (виставляє `d2dStatus`/`kdpStatus`/`googleStatus` + дати відправки). Це вже після кроку 5, ніяк не впливає на `status`/ISBN — суто зовнішній трекінг, показується автору як «Дата оновлення статистики продажів на зовнішніх майданчиках».

### Де саме в коді

- `apps/api/src/modules/books/publish.ts` — `POST /api/books/:id/publish` = крок 2 (тільки submit, без ISBN).
- `apps/api/src/modules/admin/admin.ts`:
  - `PATCH /api/admin/books/:id/approve` = крок 3 (review checkpoint).
  - `PATCH /api/admin/books/:id/publication-timeline` = кроки 4/5 — при виставленні дати на `contract_signed` виконує реальну публікацію (ISBN + `PUBLISHED`), решта кроків — просто мітки.
  - `PATCH /api/admin/books/:id/distribution` = крок 6.
- Фронтенд: `PublicationTimeline.tsx` показує весь цей ланцюг автору read-only; `PublishButton.tsx` — кнопка кроку 2 ("Надіслати на модерацію", раніше називалась "Опублікувати книгу" — перейменовано, бо не публікує напряму).

### Ключові патерни, які варто оцінити для нашого проєкту

1. **Повторна модерація при republish** — Ridero НЕ дає змінам піти live одразу; будь-яка зміна після першої публікації повертає книгу на модерацію. Це **прямо суперечить** тому, що ми зараз реалізували в `POST /api/books/:id/republish` (миттєва регенерація файлів + live без повторного рев'ю адміном) — див. відкрите питання нижче.
2. **Ліміт частоти безкоштовної републікації** — раз на 90 днів (у нас така модель відсутня, `republish.ts` дозволяє republish будь-коли, як тільки `docxUpdatedAt > publishedAt`).
3. **Чіткий діф змін** — чипи "Змінено у книзі: Текст / Вихідні дані" перед відправкою. Корисно незалежно від моделі модерації: показати автору (і потенційно адміну) що саме змінилось, а не просто "є непубліковані зміни".
4. **Модалка-підтвердження з явним попередженням про наслідки** (ліміт 90 днів) перед незворотною дією.
5. **Прозорість по кожному зовнішньому магазину окремо**: конкретна дата відправки на кожен майданчик, а не загальний статус "відправлено". У нас це частково є (`d2dSentAt`/`kdpSentAt`/`googleSentAt`), але без прогнозної дати "коли саме" до відправки.
6. **Дії "Зняти книгу з публікації"** (unpublish) — кнопка поруч з "Опублікувати у магазинах". У нас такої дії для автора немає взагалі (тільки soft-delete/архівація книги цілком, не "зняти з продажу, лишити книгу").

### Рішення (2026-08-09)

Перейшли на модель **повторної модерації** для republish — головний аргумент: правила модерації (§5.2 договору, заборона екстремізму/дезінформації/порушення авторських прав/апологетики агресії РФ) мають захищати книгу і ПІСЛЯ первинної публікації, не тільки до неї; миттєвий live без рев'ю дозволяв би підмінити вміст на заборонений. 90-денний rate-limit з Ridero свідомо НЕ перенесено — специфічний для їхньої моделі високого обсягу авторів, тоді як тут один адмін і ручний рев'ю вже є природним стримувальним фактором. Реалізація — див. T-1949 в `docs/TASKS.md`.

## 📜 Юридика

### Договір — один раз на автора, а не на книгу (задокументовано 2026-08-09, T-1951)

> Анатолій показав другий референс — реальний кабінет автора Ridero (Figma `nOXLPYS4l4mxOkCINYdQdT`,
> node-id `59-12` … `59-48`: Авторські відрахування, Загальна статистика, Мої покупки, Мої бонуси,
> Договір на публікацію, Зміна договору). Екран "Договір укладено" в референсі прямо каже: *«Умови
> договору прийняті та поширюються на всі ваші книги. Вам не потрібно укладати новий договір для
> кожної наступної книги»*.

До цього моменту було три окремі, неузгоджені місця, що чіпали `User.contractAcceptedAt`: мовчазний
автоштамп при першому «Надіслати на модерацію» (`publish.ts`), загальний сайтовий accept-bar на
`/author-agreement`, і per-book сторінка `/dashboard/books/:id/contract`, яка на кожній новій книзі
тихо перезаписувала глобальні платіжні дані автора (`taxId`/`bankIban`/`payoutDocument`).

**Рішення**: договір підписується один раз, у профілі автора (`/dashboard/settings/contract`), і
поширюється на всі книги — саме так, як `contractAcceptedAt` вже й була змодельована в схемі
(поле на `User`, не на `Book`). Наслідки:
- `POST /api/books/:id/publish` тепер **вимагає** `contractAcceptedAt` заздалегідь (код помилки
  `CONTRACT_NOT_SIGNED`) замість мовчазного автоштампу — згода стає явною дією з чекбоксами, а не
  побічним ефектом.
- Per-book сторінка `/dashboard/books/:id/contract` лишилась, але тепер це read-only місток
  (статус підписано/не підписано + посилання на профіль), а не форма підписання.
- Адмінські кроки `publicationTimeline.contract_pending/contract_corrected/review_2/contract_signed`
  (ключі не змінені, щоб не чіпати `admin.ts`/ISBN-тригер) тепер на фронтенді показуються інакше:
  `contract_pending`/`corrected`/`review_2` згорнуті в один рядок «Укладання договору» (завжди
  done, з реальною датою `contractAcceptedAt`), а `contract_signed` — це фактично «Публікація у
  магазинах» (те, чим він і був: реальний тригер ISBN + `status=PUBLISHED`), просто перейменований
  для автора, щоб не читався як друге підписання.
- «Зміна договору» (структурована KYC-форма: ПІБ, дата народження, громадянство, серія паспорта,
  адреса реєстрації, скани документа) — нові поля на `User` + приватне сховище MinIO
  (`private/identity/{userId}/...`, підписані URL, не публічні).

Реалізовано разом із чотирма новими сторінками профілю автора (Авторські відрахування — на основі
`Royalty`, Загальна статистика — MVP на реальних `Order`/`Royalty`, без вигаданих лічильників
переглядів, Мої покупки — на основі `Order`/`OrderItem`, Мої бонуси — заглушка «Незабаром», бо
концепції бонусів немає ніде в бізнес-логіці).

Автор акцептує договір один раз (при першому підписанні — див. вище). Зберігається:
- `contractAcceptedAt` — timestamp акцепту
- IP адреса — для доказової бази

Договір розміщено на `/author-agreement` (загальний текст) і `/dashboard/settings/contract`
(підписання з платіжними реквізитами). Зміна договору потребує нового акцепту.

## 🏗️ Інфраструктура

### VPS vs хмара

Обрано **VPS (Hetzner/HostGator)** а не AWS/GCP:
- Фіксована вартість (~$20-40/місяць vs $200+ на AWS для аналогічного навантаження)
- MinIO self-hosted — без S3 costs
- Простота на MVP стадії

### Reverse proxy: Caddy

- Caddy автоматично отримує та оновлює SSL сертифікати (Let's Encrypt)
- Простіша конфігурація ніж Nginx
- **Важливо**: Caddy (`dddcore-caddy-1`) — окремий проект на сервері. НЕ модифікувати без потреби.
- Routing: `/api/auth/*` → Next.js `:3000`, `/api/*` → Fastify `:3001`, все інше → Next.js `:3000`

### Docker networks

- `caddy` (= `dddcore_default`): web + api → доступні з Caddy
- `internal`: api + worker + postgres + redis + minio → ізольовані від зовнішнього світу
- `monitoring`: prometheus + grafana + node-exporter

### Monitoring

Grafana + Prometheus для метрик VPS (CPU, RAM, disk). Доступ через SSH tunnel:
```bash
ssh -L 3003:localhost:3000 user@vps  # Grafana
ssh -L 9090:localhost:9090 user@vps  # Prometheus
```
