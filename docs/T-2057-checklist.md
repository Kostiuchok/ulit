# ТЗ: єдиний рендер книги (T-2057) + чекліст реалізації/тесту

> Створено 2026-08-17. Позначати `[x]` по факту виконання, дописувати під пунктом "Реалізовано:" — як саме. Не позначати `[x]` без підпису.

## 0. Принцип

**Передперегляд = сама генерація друкованого PDF.** Немає окремого "показу" — кнопка "Передперегляд" запускає той самий рендер, що йде в друк, і показує його результат. Автор бачить не приблизну картинку, а реальний файл, який піде до друкарні.

## 0.1. КРИТИЧНО: автор сам формує макет — конвертер не має його порушувати

Автор готує `.docx` сам, у форматі A5, і сам розставляє "Зміст" із номерами сторінок, що відповідають ЙОГО власній розбивці на сторінки (як Word/LibreOffice порахували в його файлі). З цього прямо випливає:

- Конвертер **не має права**: переносити/переформатовувати абзаци, змінювати розриви сторінок, зсувати чи змінювати розмір/позицію зображень — жодних відхилень макету відносно оригінального `.docx` автора.
- Якщо конвертер це порушить — пагінація зміниться, і номери сторінок в авторському "Зміст" стануть невірними. Покупець отримає книгу зі зламаним змістом.

Це прямо конфліктує з рендером `manuscriptContent` через WeasyPrint/Puppeteer із власними CSS `@page`-правилами (розділ 3) — той підхід ре-флоу'ить контент за нашими правилами (наші шрифти/поля/розриви), що майже гарантовано дає ІНШУ пагінацію, ніж оригінальний Word-файл автора, і ламає його "Зміст". Два можливі напрями розглядались:

- **(А) Пряма конвертація оригінального `.docx`** (те, що вже й так робить сьогоднішній `generate-pdf-print.ts` через LibreOffice) — зберігає пагінацію й "Зміст" автора 1:1. Ціна: онлайн-редактор (`manuscriptContent`) не може напряму впливати на друкований файл без повторного завантаження нового `.docx`.
- **(Б) Рендер через `manuscriptContent`+WeasyPrint/Puppeteer** — дає живий передперегляд онлайн-правок, але НЕ гарантує ту саму пагінацію, що в оригінальному Word-файлі.

**РІШЕННЯ (Анатолій, 2026-08-17)**: (Б) з жорсткою вимогою вірності на обох межах конвертації — docx→редактор без втрат вмісту (жоден абзац/зображення/форматування не губиться), і редактор→PDF 1:1 (той самий рушій рендерить і передперегляд, і друк — розділ 0, не наближення). **Прийнятий і задокументований компроміс**: це НЕ відтворює точну пагінацію оригінального Word-файлу автора (жоден інший рушій рендеру не рахує перенос рядків/сторінок так само, як Word — це фізичне обмеження, не недолік реалізації). Якщо автор написав власний "Зміст" з номерами сторінок у своєму `.docx`, ці номери не гарантовано лишаться вірними після проходження через наш рендер. Оскільки авто-TOC теж прибрано зі scope (розділ 2), питання "як показати коректний Зміст" лишається відкритим на майбутнє — не блокує старт коду зараз.

## 1. Контракт рендера

```
renderManuscriptPdf(input) -> output

input:
  manuscriptContent: Json        // Book.manuscriptContent, TipTap doc
  manuscriptStyleOverrides: Json // Book.manuscriptStyleOverrides
  coverUrl?: string

output:
  pdfBuffer: Buffer
  pageCount: number              // реальна кількість сторінок готового PDF
```

Чиста функція — без побічних ефектів, без запису в БД. Різні job'и огортають її по-різному (друк додає CMYK-крок, передперегляд — ні, або взагалі показує той самий print-PDF без окремого кроку).

## 2. Структура документа

| # | Елемент | Сторінка | Опційність |
|---|---|---|---|
| 1 | Порожній форзац | verso | завжди (службова, зсуває титул на recto) |
| 2 | Титул (автор, назва, підзаголовок, видавничий імпринт) | recto | обов'язково |
| 3 | Зворот титулу (УДК/ББК, бібліографічний опис, анотація, вікове обмеження, ISBN, ©) | verso | обов'язково |
| 4 | Присвята | recto | опційно — тільки якщо автор додав |

Тіло: розділ (chapter) завжди з recto; секція/заголовок/підзаголовок нижчих рівнів розрив НЕ форсують; епіграф завжди сам на сторінці; running header зверху; номер сторінки знизу по центру.

**Зі scope T-2057 прибрано (поки що): автоматичний Зміст (TOC).** Причина: якщо автор уже написав власну сторінку "Зміст" у завантаженому `.docx` (типово для самвидаву), код зараз її не розпізнає й не видаляє (`extractOutlineFromDoc` шукає лише героям-стилізовані абзаци, авторський "Зміст" лишається звичайним текстом у тілі) — без окремого рішення це дає два "Зміст" підряд, один з яких завжди бреше про номери сторінок. Плюс невирішене питання позиції (початок vs кінець книги, конвенція Ridero) — **тепер із реальним протиріччям між джерелами**: KDP офіційно вимагає Зміст ближче до початку книги для е-книг (`docs/kdp-publishing-guide.md`, розділ 6), тоді як слов'янська видавнича конвенція (`docs/book-construction-glossary.md`) типово кладе Зміст у кінець. Якщо дбаємо про сумісність експорту з KDP — "на початку" вже не просто стилістичний вибір. Клієнтська TOC-логіка з сесії 2026-08-16 (`extractOutlineFromDoc`/`buildTocContent`/`tocEntry.ts`) лишається в коді як є, не видаляється — просто не переноситься в новий серверний рендер цим ТЗ.

## 3. Технічний рушій рендера

Puppeteer (Chromium) vs WeasyPrint (Python) — критерій: підтримка `break-before: recto` (розділ з правої сторінки нативно, без ручної логіки парності). WeasyPrint підтримує нативно, Chromium — ні (довелось би переносити ручну парність-евристику на сервер).

## 4. QA-інструмент (тимчасовий)

Додати в праву панель передперегляду кнопку **"Завантажити PDF"** — посилання напряму на файл, який показує передперегляд. Мета: дати змогу звірити байт-в-байт, що показаний передперегляд і реальний друкований документ — один і той самий файл. Прибрати кнопку, коли T-2057 підтверджено живим тестом.

Імпортер свідомо lossy (за власними коментарями коду — "author fixes up the rest"), конкретні втрати:
  - **Таблиці** — повністю відкидаються, немає вузла-таблиці в схемі редактора взагалі.
  - **Виноски** — повністю відкидаються, немає підтримки в схемі.
  - **Розриви сторінок Word** — не імпортуються (тільки ручна кнопка в редакторі створює `pageBreak`-вузол).

  - **Багатоабзацні цитати** — сплющуються в один абзац.
  - Будь-який нерозпізнаний Pandoc block/inline-тип (математика, raw-блоки, code-блоки, definition lists) — тихо відкидається (`default: return []`), без сигналу автору.
  - **Вирівнювання зображень** — деградує до "по центру" для ВСІХ зображень одразу, якщо підрахунок Pandoc AST vs сира XML не збігся (легко ламається текстовими рамками/legacy VML-картинками).
  - **Жодного автотесту** вірності імпорту в репозиторії — регресія пройде непоміченою.
